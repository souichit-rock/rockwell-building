# Browser smoke — 2026-09-30

Method: production build served by `vite preview`; every URL in `src/app/smoke.ts` loaded in two same-origin
iframes (1280 px and 390 px wide) with error hooks attached to the frame window before scripts ran; per load we
recorded console errors, uncaught errors, unhandled rejections, empty `<main>`, the "Coming up" stub text,
the Not-found card, horizontal overflow (`scrollWidth - clientWidth`) and the word "department".

## Run 1 — light theme, 53 URLs × 2 widths = 106 loads (before fixes)

| Check | Result |
| --- | --- |
| Console / uncaught errors | 0 |
| Blank or stub routes | 0 |
| Bad-id routes showing the Not-found card | 14 / 14 |
| "department" on any page | 0 |
| Slowest load (cold, incl. seed chunk) | 2.6 s |
| Horizontal overflow | 12 loads on 5 pages |

Overflow rows: `/towers/:id` (23 px at 1280, 657 px at 390), asset passport and all its tabs (196 px at 390),
`/standards` (237), `/finishes` (462), `/compliance` (328), work-order board (153 px at 1280, 1085 px at 390).

Root causes (found by hiding subtrees one at a time and re-measuring):

1. Tailwind `sr-only` is `position: absolute`. Inside a horizontally scrolling table or the board, the scroller is
   not the containing block, so the hidden span is laid out at its static x-position far to the right and
   stretches the document. Fix: `src/index.css` base rule — every `overflow-x-auto` / `overflow-auto` /
   `overflow-x-scroll` container is `position: relative`.
2. `PageHeader` and `Card` action groups were `shrink-0`, so four header buttons could not wrap on a phone.
   Fix: `min-w-0 max-w-full` instead.

## Also checked by hand

Shell in light and dark; command palette (Ctrl/Cmd-K) live search over rooms and tags; dashboard, tower
overview, floor plan with `?highlight=asset` + FIRE layer, passport, work-order board, compliance heatmap,
document detail, maintenance calendar at 1280 px; live deployment cold-loads `/a/EDS-B3-FP-01` and `/towers/grb`.

Harness notes: Chrome throttles timers in hidden tabs/windows, so the harness sleeps with a `MessageChannel`
loop instead of `setTimeout`; results are pushed to `window` per load so a timed-out tool call loses nothing.
